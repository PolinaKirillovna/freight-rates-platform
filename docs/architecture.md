# Архитектура и принципы обновления

Основной DWH построен на PostgreSQL 17. ClickHouse, Airflow и Superset дополняют обязательный контур. Ниже описана фактическая реализация текущего репозитория.

## Обоснование технологий

- **PostgreSQL 17** — основное хранилище. Перцентили (`percentile_cont`), материализованные представления с `REFRESH CONCURRENTLY`, транзакционная замена окна — всё, что нужно для честных пересчётов без внешних инструментов.
- **Python + pandas** для проверок и обогащения: правила качества — чистые векторные функции, их легко покрыть модульными тестами без базы. Перенос данных — только потоковым `COPY`, без построчных вставок.
- **SQL** для витрин: тяжёлая агрегация остаётся рядом с данными, эталонный запрос лежит отдельным файлом и читается без Python.
- **ClickHouse** — аналитический слой для больших объёмов. Коридор пересчитывается средствами самого ClickHouse (`quantileExactInclusive` интерполирует так же, как `percentile_cont`), и после каждой синхронизации ячейки сверяются с PostgreSQL.
- **CatBoost** — нативно работает с категориями (регионы, города, группа кузова), не требует масштабирования и на табличных данных стабильно обходит базовые модели. Для сравнения обучаются Ridge-регрессия и дерево решений.
- **Airflow** — расписание и повторы задач. Каждый шаг идемпотентен, поэтому повтор безопасен.
- **Superset** — дашборд создаётся автоматически при старте контейнера.
- **Конфигурация и лёгкое ООП.** Гиперпараметры обучения вынесены в `configs/ml.yaml` (путь переопределяется переменной `ML_CONFIG`), а снимок конфигурации попадает в `ml.model_runs.params`. Шаги конвейера — наследники абстрактного `PipelineStep` с общим журналированием запусков, модели — наследники `RegressionModel`.
- **DVC не используется:** данные детерминированно генерируются в PostgreSQL, оркестрация — в Airflow.

## Обновление слоёв

| Слой | Данные | Механизм обновления |
|---|---|---|
| `raw` | Снимок исходных данных | Окно `loading_date` заменяется транзакционно, справочники обновляются целиком |
| `dq` | Карантин с причинами отклонения | Перезаписывается вместе с обработанным окном |
| `core` | Очищенные факты и измерения | Окно заменяется атомарно, затронутые месяцы отмечаются для пересчёта |
| `mart` | Базовая витрина, карточка маршрута, прогнозы | Пересчёт затронутых месяцев, обновление materialized view |
| `ml` | История запусков, метрики, признаки важности | Добавляется запись каждого запуска; прогнозы заменяются снимком |
| `etl` | Журнал шагов и очередь затронутых месяцев | Журнал пополняется по шагам; очередь меняется по ходу обработки |

## Гарантии повторного запуска

Каждый шаг можно повторить за тот же период без последствий:

- извлечение и очистка заменяют окно в одной транзакции (`DELETE` + `COPY`);
- витрина пересчитывает только затронутые месяцы, полный пересчёт даёт тот же результат;
- ClickHouse заменяет секции месяцев;
- прогнозы — снимок, заменяемый целиком;
- миграции написаны через `IF NOT EXISTS`.

Это закреплено тестами: два повтора окна подряд и полный пересчёт витрин не меняют ни одного счётчика и ни одной суммы.

**Граница гарантии:** равенство бизнес-данных после повторного запуска не означает равенство технических полей (`run_id`, время выполнения, журнал запусков). Проверка приведена в [testing.md](testing.md).

## Airflow

DAG `freight_rates_pipeline` (`dags/`): `migrate → extract → transform → build_marts → [sync_clickhouse, train_and_score]`.

Окно по умолчанию скользящее: от начала интервала минус 14 дней до конца интервала плюс 150 дней. Отставание назад подхватывает поздние правки источника, например ночную разметку выбросов, а горизонт вперёд — плановые заявки для скоринга. Ручная дозагрузка за любой период:

```bash
docker compose exec airflow airflow dags trigger freight_rates_pipeline \
  --conf '{"start_date": "2023-01-01", "end_date": "2027-12-31"}'
```

Чтобы соединения в метабазе Airflow шифровались, задайте `AIRFLOW_FERNET_KEY` в `.env` — команда
для генерации ключа есть в `.env.example`.
